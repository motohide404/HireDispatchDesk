# 乗務日報

上部の「乗務日報」、または `/?view=daily` から入力する。後者は日報だけのナビゲーションを表示するスマホ・タブレット用の入口である。認証は従来の共通テストログインを使う。乗務員選択は本人認証・利用者別のアクセス制限ではない。

## 運用

年月日は最初の運行日選択1回だけ。勤務・出庫・各明細は時刻のみ入力し、保存する日時に運行日を組み合わせる。勤務開始は運行日の時刻、勤務終了は開始時刻との順序から翌日を自動判断する。終了は01:30・25:30（全角も可）を同じ翌日1:30として入力でき、当日／翌日の指定は不要。出庫・運行明細の日またぎは当日／翌日等で指定し、新規明細では直前の記録の日を初期値として引き継ぐ。保存済みの日時は画面を開いただけで書き換えない。

- 営業所は会社設定・在籍職員の営業所名・乗務員台帳の所属営業所から選択（名称の設定がない所属コードは登録どおり表示）。保存済みの日報にある旧営業所も選択肢に残す。会社設定に営業所がなければ選択した乗務員の所属を初期値にする。顧客の支店・営業所は混ぜない。
- 受書は契約ごと、運行指示書は仕事ごと、日報は乗務員・運行日ごとに1件。
- 日報を開く時に、発行済みの担当運行指示書を取得する。「この仕事を追加」で乗降地点・仕事名・指示書の版ID・予定日時を引き継ぐ。実時刻は空欄から入力する。手入力の仕事も記録できる。
- 運行明細は回送・実車・待機・休憩・交替・その他を必要なだけ追加する。待機を休憩として自動計算しない。入力画面に紙の行数を適用しない（通信・保存の技術的上限は1日1000件）。
- 最初の記録に出庫地点・実時刻・走行距離計の積算kmを入力。以降の各記録には終了時のメーター下3桁を入力する。直前との差から距離を計算し、欠けた区間を0kmとして合計しない。999→000をまたぐ区間も自動で繰り上げ計算し、運転者への確認操作は求めない。1区間1000km以上の場合は中間地点の記録を追加する。
- 未完了の入力はサーバーへ下書き保存できる。入力中は端末にも下書きを保持するが、別端末で続ける前にサーバーへ保存する。端末下書きは同じ乗務員・運行日・サーバー版と一致する場合だけ復元する。古い版を黙って上書きしない。
- 実時刻・地点・メーター等を確認して提出する。勤務開始・終了は両方とも必須。未入力のまま提出できない（途中の下書きは保存可能）。日報から出勤簿・点呼の実績を自動作成しない。
- 提出後の変更には訂正理由が必要。旧版と指示書への参照は残る。下書きも含め上書き・削除APIはない。通信失敗後の同じ保存要求は重複登録しない。別端末との競合は409で止め、入力を画面に残す。
- A4印刷のみ18行単位。最初のページの出庫行も1行に数える。19行目から次ページ、以後も18行ずつ続く。各ページに運行日・乗務員・車両番号を表示し、距離計算はページをまたいで継続する。
- 「空欄メモ用紙を印刷」で紙の記録用紙を出す。紙のメモはスマホ等に転記する運用。印刷や提出は管理者の確認を自動で完了させるものではない。

## 保存と確認

`daily_reports` テーブルへ日報の全版をJSONBで保存。共有workspaceとは分離する。乗務員・日付の排他ロックと一意制約で同時保存を保護する。保存時の乗務員名・車両番号はスナップショットとして残す。DB全体の既存バックアップ対象に含まれ、配備前後の保全ハッシュも日報を含む。自動削除はしない。

検証はNodeの距離・改ページ・予定と実績の分離、Pythonの入力・訂正・APIの検証、Playwrightの375px/768pxでの入力・復元・保存再試行・提出・訂正・PDF出力で行う。配備時は稼働DBの複製だけで実APIの保存・訂正・競合・履歴を検査する。

積算km等の記録項目の参考：近畿運輸局「業務記録（運輸規則第25条）」3ページ https://wwwtb.mlit.go.jp/kinki/content/000353363.pdf 。この機能追加だけで会社全体の運行管理や個人別権限を完成したものとは扱わない。
