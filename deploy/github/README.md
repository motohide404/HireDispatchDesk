# GitHubからの通常更新

利用者が修正のたびにMacの更新ファイルを実行する方式を終了し、HALがGitHub保存・検証・公開確認まで担当するための構成です。

## 現在の状態

- PR／作業ブランチでNode・Pythonの検証、本番ビルド、配備物の生成を実行します。
- mainの配備では、同じ成果物を専用の制限付きSSH鍵で既存のテスト環境へ送信します。
- 固定の受信処理がコード照合、バックアップ、複製DB検査、入替、データ保持、失敗時の復旧を行います。
- 公開HTML・JS・CSS・版情報の一致とHTTPS正常応答を確認します。
- **初回の環境設定と最初の実配備は未完了です。自動配備は未有効化です。**

## 初回の管理者設定

通常の利用者の更新手順にはしません。既存の管理接続から一度だけ設定します。

1. 専用Ed25519鍵と、対象ホスト名・既知の稼働ファイルのSHA-256を含む初期照合JSONを用意します。実値は運用側で管理し、Gitへ入れません。
2. 対象の既存サーバーで、rootとして `bash deploy/github/install.sh /path/to/deploy-key.pub /path/to/bootstrap.json` を実行します。照合JSONの対象ホストと全ファイルが一致しない場合は停止します。
3. GitHub Environment `sakura-test`を作成し、配備対象ブランチをmainへ限定します。次のSecretsを設定します。

| 名前 | 内容 |
| --- | --- |
| `SAKURA_SSH_KEY` | 配備専用秘密鍵 |
| `SAKURA_SSH_HOST` | 管理対象の接続先 |
| `SAKURA_SSH_KNOWN_HOSTS` | 事前確認した対象サーバーの公開ホスト鍵行 |
| `SAKURA_PUBLIC_URL` | 公開確認用のHTTPS URL |

4. リポジトリレベルのActions Variable `SAKURA_AUTO_DEPLOY`を`true`にします。ジョブ開始前の条件に使うため、環境レベルには置きません。
5. 初回のmain配備を実行し、Actions成功、公開版情報のコミット一致、データ保持まで確認した後に「運用開始済み」と記録します。

既存のMac用秘密鍵、管理者パスワード、アプリのログインパスワードをCIへ渡しません。接続先や実環境の構成を公開コードへ固定しません。

## 配備の境界

専用アカウントは `restrict` とforced command付きの鍵から固定の `update` 処理だけを受け付けます。sudoも固定の受信処理だけです。アップロードしたroot用プログラムは実行せず、初回に設置した受信・更新処理を使用します。

受信時にリポジトリ・main・完全なコミットSHA・公開版情報・サイズ・通常ファイルのみの構成・許可パス・全SHA-256を照合します。管理中のコードが外部から変更されていれば停止します。配備の失敗で管理状態を進めないことも検査します。

業務データや認証設定は配備物に含めません。APIと画面のバックアップ、一時DBに復元してのAPI検査、失敗時のプログラム復旧を既存の処理から引き継ぎます。

## 確認

- アプリの正常応答：公開先の `/api/health`。
- 公開版情報：`/build.json`。GitHub配備を初めて実行するまでは存在しません。
- データ保持・バックアップ：運用側の完了記録。
- CI成功・配備成功・公開確認・実ブラウザ操作を別々に記録します。
